AI Coding Agent(Claude Code)와 함께 개발하면서 생긴 문제, 요청 내용, 해결 방법을 날짜순으로 기록합니다.
실제로 확인한 결과만 적습니다. 아직 확인하지 못한 항목은 "미확인"으로 표시합니다.

## 2026-10-24 — v1 프로토타입 점검

**상황:** 1차 아이디어로 만든 프로토타입(v1)을 점검했다.

| 점검 항목 | 결과 |
|---|---|
| 단위 테스트(`node tests.mjs`) | 통과 |
| 회의록 작성 방식 | 원문 문장을 키워드 규칙으로 골라 그대로 옮기는 방식. **AI 요약이 아님** |
| 음성 인식 | 브라우저 안에서 돌리는 Whisper Tiny(작은 음성 인식 모델). 한국어 정확도가 낮고 실제로 테스트한 적 없음 |

**판단:** 과제의 핵심이 "실제로 작동하는 기능"이라서, 회의록 작성을 진짜 AI(Gemini)로 바꾸기로 했다.

**선택:** Google Gemini API
- 무료로 쓸 수 있는 범위가 있다.
- 녹음 파일을 직접 넣으면 받아쓰기와 회의록 작성을 한 번에 처리한다.
- 캘린더는 기존 방식(구글 캘린더 등록 화면 링크 + .ics 파일)을 유지한다. 구글 로그인 연동(OAuth: 다른 서비스에 내 계정 권한을 빌려주는 인증 방식)은 설정 부담이 커서 이번 범위에서 뺐다.

## 문제 1 — 폴더 이름이 깨져 있음

- **문제:** 프로젝트 폴더 이름이 `MeetMate_%EC%9B%B9%EC%95%B1...`처럼 URL 인코딩된 상태였다(한글이 컴퓨터용 코드로 바뀐 모습). GitHub 저장소 이름이나 Vercel 프로젝트 이름이 이상해질 수 있다.
- **해결:** `meetmate` 폴더를 새로 만들어 파일을 복사했다. 원본 폴더는 그대로 보존했다.

## 문제 2 — Gemini 공식 문서의 예제가 새 API로 바뀌어 있음

- **문제:** 최신 Gemini 문서의 예제는 새로 나온 Interactions API 기준으로 쓰여 있었다.
- **조사:** 같은 문서에 기존 `generateContent` API가 "계속 완전히 지원된다(fully supported)"고 적혀 있었다.
- **해결:** 자료가 많고 응답 형식이 안정적인 `generateContent`를 쓰기로 했다. 모델은 문서에서 새 프로젝트용으로 추천한 `gemini-3.8-flash`이고, 무료 등급에서도 쓸 수 있다. 모델 이름은 환경 변수 `GEMINI_MODEL`로 바꿀 수 있게 했다.

## 문제 3 — 서버가 큰 녹음 파일을 한 번에 받지 못함 (1차 해결 실패 → 2차 해결)

- **문제:** Vercel 서버 함수는 요청 하나에 최대 4.5MB까지만 받는다. 회의 녹음은 보통 수십 MB다.
- **1차 시도:** 파일을 3.5MB씩 나눠 서버로 보내고, 서버가 Gemini로 이어 보내는 방식(조각 중계)을 만들었다.
- **실제 테스트 결과 실패:** 5.8MB 테스트 녹음을 올리자 Gemini가 400 오류를 돌려줬다. 처음에는 오류 이유가 비어 있었다. 코드가 오류 내용을 JSON일 때만 읽고 있었기 때문이다. 오류 원문까지 보이게 고치고 다시 실행하자 진짜 원인이 나왔다:
  > The client sent 3670016 bytes, which is not a multiple of the 8388608 byte chunk granularity.

  Gemini는 중간 조각을 **8MB 단위로만** 받는데, Vercel은 **4.5MB까지만** 받는다. 두 조건이 동시에 성립할 수 없으므로 이 방식은 구조적으로 불가능했다.
- **2차 해결:** 서버는 API 키로 **업로드 주소만 발급**하고, 파일은 브라우저가 Google로 **직접** 올린다. 업로드 주소는 그 파일 하나만 올릴 수 있는 일회용 주소라 API 키가 노출되지 않는다.
- **새 문제와 해결 (CORS):** 브라우저는 다른 사이트(Google)의 허락이 있어야 요청 결과를 읽을 수 있다(CORS라는 보안 규칙). 확인해 보니 사전 확인(preflight)은 통과했지만, 실제 업로드 응답에는 허락 헤더(`Access-Control-Allow-Origin`)가 없었다. 업로드 주소를 처음 발급받을 때 서버가 브라우저의 출처(Origin) 정보를 Google에 함께 전달하도록 바꾸자 허락 헤더가 정상으로 붙었다.
- **결과:** 최대 200MB까지 브라우저에서 직접 업로드한다. 진행률(%)도 표시된다.

## 문제 4 — Gemini가 읽지 못하는 녹음 형식

- **문제:** Gemini 문서에 나온 지원 형식은 wav, mp3, aac, ogg, flac, aiff다. 휴대폰 녹음 앱이 자주 쓰는 m4a와 브라우저 녹음 파일(webm)은 목록에 없다.
- **해결:** 목록에 없는 형식은 브라우저가 소리를 풀어서(디코딩) 16kHz 모노 WAV로 바꾼 다음 올린다. 메모리 문제 때문에 이 변환은 40분 이내 녹음으로 제한했다.
- **확인:** 브라우저 테스트에서 m4a 형식으로 지정한 파일이 WAV로 변환된 뒤 회의록까지 정상으로 만들어지는 것을 확인했다(7초).
- **미확인:** 실제 아이폰이나 갤럭시로 녹음한 m4a 파일로는 아직 테스트하지 않았다. 테스트 파일은 WAV 내용에 m4a 이름을 붙인 것이다.

## 문제 5 — 개인정보 안내 문구가 사실과 달라짐

- **문제:** v1 화면에는 "음성파일은 서버로 업로드하지 않습니다"라고 적혀 있었다. Gemini를 쓰면 녹음이 Google 서버로 전송되므로 이 문구는 사실이 아니게 된다.
- **해결:** 문구를 "AI 처리를 위해 보낸 녹음 파일은 처리 직후 삭제됩니다"로 바꿨다. 실제로 회의록을 만든 직후 Gemini에서 파일을 삭제하는 코드를 넣었다(삭제하지 않아도 48시간 뒤에는 자동으로 지워진다).

## 문제 6 — 업로드 중계 기능이 악용될 가능성

- **문제:** `/api/upload`는 브라우저가 알려준 주소로 데이터를 전달한다. 아무 주소나 허용하면 남이 우리 서버를 다른 사이트 공격용 중계기로 쓸 수 있다(SSRF라는 보안 취약점).
- **해결:** `https://generativelanguage.googleapis.com/`으로 시작하는 주소만 허용했다.
- **확인:** `https://evil.com` 주소로 보낸 요청이 400 오류("잘못된 업로드 주소입니다")로 차단되는 것을 확인했다.

## 문제 7 — AI가 실패하면 앱 전체가 멈출 위험

- **문제:** API 키 누락, 무료 사용량 초과, 인터넷 끊김이 생기면 회의록을 아예 만들 수 없게 된다.
- **해결:** 텍스트 정리는 AI가 실패하면 v1의 규칙 기반 추출로 자동 전환한다. 화면에는 "규칙 기반 결과"라고 분명히 표시한다.
- **확인:** API 키가 없는 상태에서 서버가 "서버에 GEMINI_API_KEY가 설정되지 않았습니다" 오류를 돌려주는 것을 확인했다.

## 문제 8 — AI 응답이 너무 느림 (2분 35초)

- **문제:** 첫 실제 호출에서 짧은 메모 하나를 정리하는 데 **2분 35초**가 걸렸다. 결과 품질은 좋았다.
- **원인 추정:** Gemini 3 계열 모델은 기본적으로 답하기 전에 깊게 "생각(thinking)"한다.
- **시도 1:** 생각 수준을 `low`로 낮췄다 → **1분 19초**. 아직도 길다.
- **시도 2:** 더 가벼운 모델 `gemini-3.5-flash-lite`로 바꿨다 → **2초**.
- **비교:** 같은 메모에서 두 모델이 뽑은 할 일 3개(담당자, 기한)는 똑같이 정확했다. 요약 문장은 flash 쪽이 조금 더 풍부했다.
- **결정:** 기본 모델을 flash-lite로 정했다. 환경 변수 `GEMINI_MODEL`로 언제든 바꿀 수 있다.

## 문제 9 — AI가 담당자를 지어냄 (환각)

- **문제:** 녹음 테스트 중 "이벤트 경품 리스트는 **제가** 이번 주 금요일까지 정리하겠습니다"의 담당자가 **김민수**로 나왔다. 바로 앞 문장에 나온 사람이다. 같은 녹음으로 한 앞선 테스트에서는 빈칸이었다. AI는 같은 입력에도 매번 조금씩 다르게 답한다.
- **배운 점:** 프롬프트로 "지어내지 마세요"라고 해도 100% 막을 수는 없다. AI의 답을 코드로 한 번 더 검사해야 한다.
- **해결:**
  1. 프롬프트에 "앞 문장에 나온 다른 사람의 이름을 짐작해서 넣지 마세요"를 추가했다.
  2. `verifiedOwner()` 함수를 추가했다. AI가 근거로 인용한 문장 안에 담당자 이름(전체 이름 또는 "소연"처럼 이름 두 글자)이 실제로 있을 때만 담당자를 남기고, 없으면 비운다.
- **결과:** 단위 테스트 3건(지어낸 이름은 제거, 정상 이름은 유지, 이름만 부른 경우는 유지)을 통과했다. 다시 돌린 브라우저 테스트에서도 해당 할 일의 담당자가 "미정"으로 표시됐다.
- **한계:** 근거 문장에 이름이 없고 앞 문장에만 있는 정상적인 경우에도 담당자가 비워질 수 있다. 틀린 사람이 들어가는 것보다 빈칸이 안전하다고 판단했다. 빈칸은 사용자가 직접 채우면 된다.

## 2026-10-24 — 방향 전환: "클로바노트 없이 앱 하나로"

**사용자 피드백:** 평소에는 녹음 → 클로바노트에 올려 받아쓰기 → 텍스트 복사 → 정리 순서로 일하는데, 이 과정이 너무 번거롭다. 애플 받아쓰기는 화자 구분이 안 돼서 클로바노트를 쓰게 된다.

**결정:** MeetMate 안에서 녹음부터 캘린더까지 끝낼 수 있게 한다. 더 정교한 받아쓰기가 필요한 사람은 클로바노트 텍스트를 붙여넣어 쓰면 된다.

**AI에게 요청한 변경:**
1. 녹음 종료 → 자동으로 AI 처리 (버튼 한 번 줄이기)
2. 화자 구분 강화 (목소리로 화자를 나누고, 대화에서 이름을 찾고, "제가"라고 말한 사람을 담당자로 연결)
3. 화자 이름 바꾸기 화면
4. 클로바노트 텍스트 붙여넣기 안내 (화자 표시 "참석자 1"도 인식)

**설계 — AI가 하는 일과 규칙이 하는 일을 나눴다:**
- **AI(Gemini):** 받아쓰면서 화자를 `화자1`, `화자2`로 구분한다. 대화 속 근거(예: "민수 씨?"라고 부르자 대답함)가 분명할 때만 `화자2 = 김민수`처럼 이름을 추정한다. "제가 할게요"의 담당자에는 화자 표시를 적는다.
- **규칙(`renameSpeakers`):** AI가 추정한 이름이나 사용자가 고친 이름을 원문, 회의록, 할 일에 **찾아 바꾸기**로 반영한다. AI를 다시 부르지 않아서 즉시 반영되고 비용도 들지 않는다.

## 문제 10 — 이름 바꾸기에서 생길 수 있는 오류 두 가지 (미리 막음)

- "화자1"을 김민수로 바꿀 때 "화자10"이 "김민수0"이 되는 문제 → 숫자로 끝나는 이름 뒤에 숫자가 이어지면 바꾸지 않게 했다.
- 두 사람 이름을 맞바꿀 때(김민수↔박지현) 차례로 바꾸면 둘 다 같은 이름이 되는 문제 → 모든 이름을 한 번에 동시에 바꾸게 했다.
- 단위 테스트로 두 경우 모두 확인했다.

## 문제 11 — 셸 명령으로 코드를 쓰다가 역슬래시(\)가 사라짐

- **문제:** AI 에이전트가 터미널 명령으로 코드를 파일에 쓰자, 정규식의 `\`가 `\`로 줄어들어 문법 오류(`Invalid regular expression`)가 났다. 테스트 코드의 `\n`은 실제 줄바꿈으로 바뀌었다.
- **해결:** 특수문자가 들어간 코드는 셸 명령이 아니라 파일 편집 도구로 직접 고쳤다.
- **배운 점:** AI가 만든 코드도 바로 실행해서 확인해야 한다. 이번에도 단위 테스트를 바로 돌린 덕분에 즉시 발견했다.

## 화자 구분 테스트 결과

**테스트 녹음:** 컴퓨터에 한국어 음성이 하나(Heami)뿐이라서, 같은 목소리의 높낮이와 속도를 바꿔 세 사람을 흉내 냈다. 실제 사람 목소리보다 구분하기 어려운 조건이다. 참석자는 김민수, 박지현, 최유나다.

## 2026-10-25 — 회의록을 "실제 보고서 수준"으로

**사용자 피드백:** 회의록이 더 상세하고 바로 쓸 수 있는 수준이면 좋겠다. 평소 미팅 리포트는 "주요 내용 / 우리가 해야 할 일 / 클라이언트가 해야 할 일"로 쓰는데, 내부 회의에도 쓸 수 있게 "주요 내용 / 해야 할 일"로 크게 나누자.

**실제 미팅 리포트 예시를 받아 분석한 특징:**
- 주요 내용은 안건별 번호(1. 프로모션 리플릿, 2. 제품 리플릿…) 아래 3~5개 항목. 각 항목이 "무엇을 어떻게 하기로 했는지 + 이유·조건·예외"까지 담긴 완결된 문장.
- 해야 할 일은 조직별(시하 / 세스코)로 나뉘고, 각 항목 아래 세부 작업이 있으며 기한은 괄호로.

**AI에게 요청한 변경과 구현:**
| 항목 | 이전 | 이후 |
|---|---|---|
| 주요 내용 | 3~6줄 요약 | 안건별 번호 + 상세 항목 (이유·조건·예외·수치 포함) |
| 결정 사항 | 별도 칸 | 안건 내용 안에 "~하기로 확정"으로 녹임 |
| 해야 할 일 | 한 목록 | 조직(`team`)이 구분되면 조직별로 묶음, 내부 회의면 한 목록 |
| 할 일 세부 | 없음 | `details` 목록 (실행 목록에서 한 줄에 하나씩 편집) |
| 회의록 .md | 4개 섹션 | ■ 주요 내용 / ■ 해야 할 일(조직별, 세부 포함) / ■ 확인 필요·다음 회의 |

**기술적으로 바뀐 점:** AI 응답 양식(JSON 스키마)이 `summary/decisions/issues` → `topics[{title, points[]}] / tasks[{title, details[], team, owner, due, evidence}] / issues / nextMeeting / speakers`로 바뀌었다. 화면에서는 안건 구조를 "1. 제목 / - 항목" 형식의 텍스트로 바꿔 보여 주므로, 사용자가 자유롭게 고칠 수 있다.

**테스트 (가상의 에이전시–클라이언트 회의 메모, 러프한 메모 형식):**
- 4.5초 만에 안건 3개(각 3~4개 항목), 할 일 6개(민트 3 / 한빛 3), 확인 필요 2개, 다음 회의 일정이 나왔다.
- "소연 과장이 두 군데 받아서 다음 주 수요일까지 공유" → 담당 전소연, 기한 2026-10-28, 세부 2개("인쇄소 두 군데 견적 받기", "견적 내용 공유").
- "이유: CS 피드백 있었음" 같은 근거가 주요 내용에 그대로 들어갔다.
- 실행 목록에서 세부 사항을 고치면 회의록 .md에 바로 반영되는 것을 확인했다.

## 2026-10-25 — 회의록 양식 학습: "기존 회의록 샘플을 하나 올려주세요"

**사용자 아이디어:** 앱을 처음 열 때 기존 회의록 샘플을 올리게 하고, 그 양식대로 회의록을 내보내자. 샘플이 없으면 추천 양식으로. 아이콘도 만들자.

**설계 (AI와 규칙의 분담):**
- 양식은 회의 데이터와 **별도로** 브라우저에 저장한다(`meetmate-template`). "전부 지우기"를 눌러도 양식은 남는다.
- 회의록을 만들 때마다 샘플 전문(최대 8,000자)을 Gemini에 함께 보내고, "구조·제목 체계·번호·기호·말투는 따르되 내용은 가져오지 말 것"을 지시한다. AI는 기존 결과(안건·할 일·화자)에 더해 `formatted`(샘플 양식으로 쓴 회의록 전체)를 하나 더 돌려준다.
- 할 일 추출과 캘린더 기능은 양식과 상관없이 그대로 돈다. 양식은 "회의록 본문을 어떤 모양으로 쓸지"만 정한다.
- 내 양식을 쓴 경우 회의록 .md 다운로드는 그 본문을 **그대로** 내보낸다(추천 양식 머리말을 덧붙이지 않는다).
- .txt/.md는 바로 읽고, .docx는 압축 파일 안의 `word/document.xml`에서 글자만 뽑는다(JSZip 라이브러리, 필요할 때만 내려받음).
- 앱 아이콘: 말풍선(회의) 안에 체크(완료) 모양의 SVG. 브라우저 탭 아이콘과 사이드바 로고에 같이 쓴다.

**테스트 (실제 미팅 리포트 양식을 샘플로, 예시 회의를 입력):**
| 확인 | 결과 |
|---|---|
| 첫 방문에 양식 선택 창이 열림 | ✅ |
| .txt 샘플 올리기 → 사이드바에 "내 양식 · 파일명" | ✅ |
| 예시 회의 → 샘플 양식으로 회의록 | ✅ 5초. `■ 오늘 회의 주요 내용 / [묶음] / 1. 항목` 구조, `■ 민트스튜디오 진행 예정 사항`, `<한빛식품 확인 및 전달 요청 사항>`까지 샘플의 조직 표기 방식을 따라 씀 |
| 샘플 내용(세스코, 리플릿 등)이 새 회의록에 섞여 들어가는지 | ✅ 섞이지 않음 |
| .md 다운로드가 양식 그대로인지 | ✅ |
| 새로고침 후 양식 기억, 창 다시 안 뜸 | ✅ |
| 추천 양식으로 되돌리기 | ✅ |
| .docx 읽기 | ✅ (테스트용으로 만든 작은 docx) |
| 모바일 레이아웃 | ✅ 가로 넘침 없음 |

**관찰된 한계:** 양식 모드에서 "인쇄소 견적 공유(전소연)"가 할 일 목록에는 있었지만 `■ 진행 예정 사항` 본문에서는 빠졌다. AI가 formatted와 tasks를 따로 쓰기 때문에 둘이 완전히 일치하지 않을 수 있다. 할 일 목록 쪽이 기준이고, 본문은 사용자가 보고 보완해야 한다.

## 2026-10-27 — 배포 준비: 접속 코드, README, 스크린샷

**왜 접속 코드인가:** 공개 주소가 생기면 누구나 내 Gemini 무료 사용량을 쓸 수 있다. 로그인 기능을 만들기엔 과하고, 서버 환경 변수 `ACCESS_CODE` 하나로 막는 게 과제 규모에 맞다.

**구현:**
- 서버: `ACCESS_CODE`가 설정돼 있으면 모든 API 요청의 `x-access-code` 헤더와 비교해 다르면 401. 설정이 없으면 검사하지 않는다(로컬 개발 편의).
- 브라우저: 401을 받으면 코드 입력 창을 한 번 띄우고, 입력한 코드를 브라우저에 저장한 뒤 같은 요청을 다시 보낸다. 이후 요청에는 자동으로 붙인다.
- 단위 테스트 4건(미설정 → 통과, 빈 코드 → 401, 틀린 코드 → 401, 맞는 코드 → 통과).

**브라우저 테스트:** 코드 없이 정리 → 입력 창 → 틀린 코드 → "접속 코드가 맞지 않습니다" 안내와 함께 규칙 기반으로 전환 → 맞는 코드 → AI 회의록 성공 → 새로고침 후에도 창 없이 바로 성공.

**README 재작성:** v1(Whisper) 기준이던 내용을 현재 구조(Gemini, 양식 학습, 화자 구분, 접속 코드, Vercel 배포)로 다시 썼다. 스크린샷 4장(첫 화면, 양식 선택, 회의록, 할 일)도 새 화면으로 다시 찍었다. v1 보고서 초안(REPORT_TEMPLATE.md)은 내용이 맞지 않아 지우고, 최종 보고서는 배포 후 실제 주소와 테스트 결과를 넣어 새로 쓴다.

### 문제 13 — push가 403으로 거부됨
- **문제:** `git push`가 "Permission denied to cescomktsh-wq"로 실패했다. 이 컴퓨터에 회사 GitHub 계정의 로그인 정보가 저장돼 있어서 그 계정으로 올리려 한 것이다.
- **시도 1:** 이 저장소만 개인 계정(`yimdahae-hub`)으로 로그인하도록 설정하자 브라우저 승인 창이 떴는데, 승인 범위에 회사 조직 접근까지 포함돼 있어 사용자가 승인하지 않기로 했다.
- **해결:** 저장소 하나(meetmate)에만, 코드 쓰기 권한만 가진 **세분화 토큰(fine-grained PAT)** 을 만들어 그걸로 로그인했다. 회사 조직에는 아무 권한도 주지 않는다.
- **배운 점:** 한 컴퓨터에서 GitHub 계정을 두 개 쓰면 로그인 정보가 섞인다. 저장소별로 어떤 계정을 쓸지 git 설정(`credential.<url>.username`)으로 지정할 수 있다.

### 문제 14 — AI 에이전트의 안전장치가 원격 주소 변경을 막음
- **문제:** 처음에 GitHub 아이디를 잘못 알고 주소를 넣었다가 고치려 하자, AI 에이전트의 안전장치가 "원격 저장소 주소 변경"을 자동 승인하지 않았다. 코드를 엉뚱한 곳에 보낼 수 있는 작업이라서다.
- **해결:** 명령을 사용자가 직접 실행했다(더블클릭용 .cmd 파일을 만들어 실행). 한글 메시지가 깨지며 창이 닫혔지만 주소 변경은 성공했다.

### 문제 15 — Vercel 환경 변수 Key/Value를 반대로 입력
- **문제:** "Key" 칸에 API 키 값을 넣어서 "이름에는 영문·숫자·밑줄만 쓸 수 있다"는 오류가 났다. Key는 변수 **이름**(`GEMINI_API_KEY`), Value가 실제 키라는 점이 처음엔 헷갈린다.
- **해결:** 칸을 바꿔 넣었다. 이 과정에서 키 일부가 캡처 화면에 노출됐지만 대화 밖으로 나가지 않았다. 앞으로 키가 보이는 화면은 캡처하지 않기로 했다.

### 문제 16 — 접속 코드 창에서 Enter를 누르면 "입력하지 않았어요"
- **문제:** 코드를 입력하고 Enter를 누르면 취소로 처리됐다. HTML 폼은 Enter를 누르면 **첫 번째 버튼**을 누른 것으로 보는데, 취소 버튼이 먼저 있었다.
- **해결:** 확인 버튼을 폼의 첫 버튼으로 옮기고, 취소는 일반 버튼(`type=button`)으로 바꿨다. 화면에 보이는 순서는 CSS로 유지했다. 배포 주소에서 Enter로 입력되는 것을 확인했다.
