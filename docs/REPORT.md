## 1. 1분 소개 (발표용)

> 회의가 끝나면 늘 같은 일을 반복했습니다. 녹음을 클로바노트에 올려 받아쓰고, 그 텍스트를 복사해 회의록을 쓰고, 누가 뭘 언제까지 하기로 했는지 다시 정리해서 캘린더에 넣는 일입니다.
>
> MeetMate는 이 과정을 한 번에 끝냅니다. 녹음 파일이나 회의 중 급하게 적은 메모를 올리면, AI가 받아쓰고 화자를 나누고, 안건별 회의록과 담당자·기한이 붙은 할 일을 만듭니다. "다음 주 수요일까지"라고 말해도 실제 날짜로 계산해서 구글 캘린더 등록 버튼까지 붙여 줍니다.
>
> 특징은 두 가지입니다. 첫째, 처음 열 때 기존에 쓰던 회의록 샘플을 올리면 그 양식 그대로 써 줍니다. 저희 팀 미팅 리포트 양식으로 테스트했습니다. 둘째, AI 결과를 그대로 믿지 않습니다. 담당자가 근거 문장에 실제로 있는지, 화자 표시가 원문에 있는지 코드로 다시 검사하고, 틀릴 수 있는 부분은 사용자가 바로 고칠 수 있게 했습니다.
>
> 브라우저만 있으면 되고, Gemini 무료 등급으로 돌아갑니다. 녹음 70초짜리 회의가 8초 만에 회의록이 됩니다.

## 2. 주요 기능별 작동 원리

### 2-1. 전체 구조

```
[사용자 브라우저]                    [Vercel 서버 함수]                [Google Gemini]
                                    (api/minutes.js, api/upload.js)
 녹음 파일 ─── 직접 업로드 ──────────────────────────────────────▶ Files API (임시 보관, 처리 후 삭제)
             (업로드 주소만 서버가 발급)
 메모·원문 ──▶ /api/minutes ──▶ 프롬프트 + API 키 ───────────────▶ gemini-3.5-flash-lite
                                 결과 검사 ◀─────────────────────  JSON (안건·할 일·화자·양식본문)
 회의록·할 일 화면 (브라우저 localStorage에 저장)
   → 구글 캘린더 등록 화면 링크 / .ics 파일 / .md 파일
```

**용어 풀이**
- **서버 함수(Serverless Function):** 요청이 올 때만 잠깐 실행되는 작은 서버 프로그램. 항상 켜 둘 서버가 필요 없어서 무료로 운영할 수 있다.
- **API 키:** Gemini를 쓸 수 있게 해 주는 비밀번호. 브라우저 코드에 넣으면 누구나 볼 수 있어서 서버 함수에만 둔다.
- **localStorage:** 브라우저 안의 작은 저장 공간. 서버 없이 데이터를 보관하지만 그 브라우저에서만 보인다.

### 2-2. 기능별 설명

| 기능 | 사용자에게 하는 역할 | 작동 원리 | AI / 규칙 |
|---|---|---|---|
| 녹음 파일 업로드 | 휴대폰 녹음을 그대로 올린다 | 서버가 Gemini에 "업로드 주소"를 받아 브라우저에 넘기고, 브라우저가 Google로 직접 올린다. Gemini가 지원하지 않는 형식(m4a 등)은 브라우저가 WAV로 바꿔 올린다 | 규칙 |
| 바로 녹음 | 회의 중 앱에서 녹음 | 브라우저 마이크 API로 녹음 → 종료하면 자동으로 위 업로드 과정 | 규칙 |
| 받아쓰기 + 화자 구분 | 누가 뭐라고 했는지 글로 | Gemini가 녹음을 듣고 "화자1: …" 형식으로 받아쓴다. 대화 중 이름이 불리면("민수 씨?") 그 화자의 이름을 추정한다 | **AI** |
| 화자 이름 바꾸기 | 화자1 → 실제 이름 | 원문·회의록·할 일에서 찾아 바꾸기. AI를 다시 부르지 않아 즉시 반영 | 규칙 |
| 회의록 작성 | 안건별 상세 회의록 | Gemini에 회의 날짜, 참석자, 3주치 달력표, 작성 규칙을 함께 보내고 정해진 JSON 양식으로 받는다 | **AI** |
| 할 일 추출 | 누가·무엇을·언제까지 | 같은 요청에서 tasks 배열로 받는다. "다음 주 수요일" 같은 상대 날짜는 달력표를 보고 AI가 계산 | **AI** |
| AI 결과 검사 | 엉뚱한 담당자·날짜 방지 | 담당자 이름이 근거 문장에 실제로 있는지, 화자 표시가 원문에 있는지, 날짜 형식이 맞는지, 두 화자에 같은 이름이 붙지 않았는지 코드로 확인 | 규칙 |
| 회의록 양식 학습 | 우리 팀 양식 그대로 | 샘플 전문을 요청마다 함께 보내고 "구조·기호·말투만 따르고 내용은 가져오지 말 것"을 지시 | **AI** |
| 캘린더 등록 | 할 일 → 일정 | 구글 캘린더 "일정 만들기" 화면을 제목·날짜·설명이 채워진 주소로 연다. .ics는 표준 일정 파일 형식으로 직접 생성 | 규칙 |
| 접속 코드 | 모르는 사람의 사용 차단 | 서버 환경 변수와 요청 헤더의 코드를 비교. 틀리면 401 | 규칙 |
| AI 실패 시 예비 경로 | 인터넷·키 문제여도 동작 | 원문에서 "결정", "해주세요" 같은 단어가 든 문장을 골라내는 v1 규칙 로직으로 자동 전환, 화면에 "AI 연결 실패" 표시 | 규칙 |

### 2-3. 데이터가 지나가는 길 (녹음 파일 기준)

1. 사용자가 mp3 파일을 올린다.
2. 브라우저가 서버 함수 `/api/upload`에 "이 크기·형식의 파일을 올리겠다"고 알린다. 서버는 API 키로 Gemini에 업로드 주소를 받아 브라우저에 돌려준다. (파일 자체는 서버를 거치지 않는다. 서버 함수는 요청 하나에 4.5MB까지만 받기 때문)
3. 브라우저가 그 주소로 파일을 Google에 직접 올린다. 진행률이 표시된다.
4. 브라우저가 `/api/minutes`에 파일 이름과 회의 정보를 보낸다.
5. 서버가 Gemini에 프롬프트(작성 규칙 + 달력표 + 양식 샘플)와 파일을 함께 보낸다.
6. Gemini가 JSON으로 받아쓰기, 안건, 할 일, 화자, (양식 본문)을 돌려준다.
7. 서버가 결과를 검사하고(담당자 근거, 화자 표시, 날짜), Gemini에서 녹음 파일을 삭제한다.
8. 브라우저가 화면에 표시하고 localStorage에 저장한다. 사용자가 고치면 바로 저장된다.
9. "구글 캘린더에 등록"을 누르면 날짜·제목이 채워진 캘린더 화면이 새 탭으로 열린다.

### 2-4. 기술 선택 이유

| 기술 | 역할 | 선택 이유 |
|---|---|---|
| HTML / CSS / JavaScript (프레임워크 없음) | 화면과 동작 | 빌드 도구 없이 파일 그대로 실행·배포된다. 구조를 이해하고 설명하기 쉽다 |
| Google Gemini (`gemini-3.5-flash-lite`) | 받아쓰기, 회의록, 할 일 | 무료 등급이 있고 녹음 파일을 직접 받는다. 상위 모델(3.8-flash)은 같은 메모에 1~2분이 걸렸고 할 일 정확도는 같아서 가벼운 모델을 택했다 (DEVLOG 문제 8) |
| Vercel 서버 함수 | API 키 보호, Gemini 호출 | 무료, GitHub에 올리면 자동 배포 |
| localStorage | 회의 데이터 저장 | 서버·DB 없이 동작. 대신 브라우저 하나에 묶인다 |
| 구글 캘린더 템플릿 URL + .ics | 일정 등록 | 구글 계정 연동(OAuth)은 설정이 복잡해 범위 밖으로 두었다. 링크 방식은 사용자가 저장 전에 확인할 수 있다는 장점도 있다 |

## 3. 교수님이 질문할 만한 내용 5가지

**Q1. AI가 한 일과 직접 만든(규칙) 부분을 구분해 설명해 보세요.**
AI(Gemini)는 받아쓰기, 화자 구분, 회의록 문장 작성, 할 일·담당자·기한 추출, 양식 따라 쓰기를 합니다. 규칙 코드는 그 결과를 검사하고(담당자가 근거 문장에 있는지 등), 화자 이름 바꾸기, 캘린더 링크와 .ics 생성, 저장, 접속 코드, AI 실패 시 예비 경로를 담당합니다. 2-2 표에 기능별로 표시했습니다.

**Q2. 그냥 노션 AI나 클로바노트를 쓰면 되지 않나요?**
클로바노트는 받아쓰기를 잘하지만 회의록 양식과 할 일·캘린더는 다시 손으로 해야 합니다. 노션 AI 회의록은 월 $20 유료 요금제가 필요하고, 화자 표시는 영어만 지원하며, 결과가 일반 요약이라 우리 양식으로 옮겨 써야 합니다. MeetMate는 "정해진 양식의 회의록 + 캘린더 일정"이라는 마지막 단계에 집중했고, 한국어 녹음에서 화자를 나눕니다. 다만 실시간 받아쓰기와 받아쓰기 정확도는 전문 서비스가 더 낫습니다.

**Q3. AI가 틀리면 어떻게 하나요?**
세 겹으로 대비했습니다. ① 프롬프트에 "지어내지 말 것", "근거 문장 인용"을 요구하고 ② 코드가 결과를 검사해 근거 없는 담당자는 비우고 ③ 모든 결과를 사용자가 화면에서 바로 고칠 수 있게 했습니다. 실제로 테스트 중 AI가 "제가 하겠습니다"의 담당자에 앞 문장의 다른 사람 이름을 넣은 적이 있어 ②를 추가했습니다 (DEVLOG 문제 9). 화자 구분은 세 명을 흉내 낸 녹음에서 발언 6개 중 1개가 틀렸습니다.

**Q4. API 키는 어떻게 보호하나요? 왜 서버가 필요한가요?**
키를 브라우저 코드에 넣으면 개발자 도구로 누구나 볼 수 있습니다. 그래서 키는 Vercel 서버 함수의 환경 변수에만 두고, 브라우저는 서버에 부탁만 합니다. 녹음 파일은 서버가 "일회용 업로드 주소"만 발급하고 브라우저가 Google로 직접 올리므로 키가 노출되지 않습니다. 공개 주소에서는 접속 코드로 모르는 사람의 사용을 막습니다.

**Q5. 개발하면서 가장 어려웠던 문제는 무엇이고 어떻게 해결했나요?**
녹음 파일 업로드입니다. 처음엔 파일을 3.5MB씩 나눠 서버를 거쳐 Gemini로 보내게 만들었는데, 실제로 돌려 보니 Gemini는 중간 조각을 8MB 단위로만 받고 Vercel은 요청당 4.5MB까지만 받아서 구조적으로 불가능했습니다. 오류 메시지 원문을 읽고 나서야 원인을 알았고, "서버는 주소만 발급, 브라우저가 직접 업로드" 구조로 바꿨습니다. 그 뒤 브라우저 보안 규칙(CORS) 문제가 또 생겨 서버가 브라우저의 출처 정보를 Google에 전달하도록 고쳤습니다 (DEVLOG 문제 3).

**(예비) Q6. 데이터는 어디로 가나요?**
회의록은 사용자 브라우저에만 저장됩니다. 녹음과 메모는 Google Gemini로 전송되고, 무료 등급에서는 Google이 제품 개선에 쓸 수 있습니다. 그래서 앱 안내와 README에 기밀 회의는 넣지 말라고 적었고, 녹음 파일은 처리 직후 Gemini에서 삭제합니다.

## 4. AI Coding Agent를 어떻게 활용했나

**역할 분담:** 사용자는 문제 정의, 기능 우선순위, 화면 문구 검토, 실제 데이터로 결과 판단을 맡았고, AI 에이전트(Claude Code)는 설계 제안, 코드 작성, 테스트 실행, 문서 작성을 맡았습니다. 모든 변경은 "무엇이 달라졌고 어떤 원리인지" 설명을 받은 뒤 다음 단계로 갔습니다.

**진행 과정 (요약)**
1. v1 프로토타입 점검 → 회의록이 규칙 기반 문장 복사에 그친다는 한계 확인 → Gemini 도입 결정
2. 서버 함수 설계, 프롬프트와 JSON 응답 양식 작성, 로컬 개발 서버 구성
3. API 키 발급 후 실제 호출 → 2분 35초 지연 발견 → 모델·설정 변경으로 2초
4. 윈도우 음성 합성으로 테스트 녹음을 만들어 녹음 경로 검증 → 업로드 구조 실패 → 재설계
5. 사용자 피드백 반영: 클로바노트 없이 앱 하나로(화자 구분·자동 처리), 실제 보고서 수준의 상세 회의록, 화면 문구에서 번역투 제거, 기존 회의록 샘플로 양식 학습
6. 접속 코드, README·스크린샷 정리, GitHub 업로드, Vercel 배포, 배포 환경 재테스트

**AI에게 요청한 수정 예시**
- "AI가 담당자를 지어낸다" → 근거 문장에 이름이 있을 때만 인정하는 검사 추가
- "텍스트 입력인데 참석자가 화자로 뜬다" → 원문에 `이름:` 표시가 있을 때만 화자로 인정
- "'회의가 끝나면, 실행이 시작됩니다'가 어색하다" → 화면 문구 40여 개 전면 점검

**검증 방법:** 단위 테스트(`node tests.mjs`, 날짜 계산·담당자 검사·.ics·양식·접속 코드 등 30여 건)와 Edge 브라우저 자동 테스트(녹음 업로드부터 캘린더 링크까지)를 변경 때마다 돌렸습니다. AI가 만든 코드에서 터미널 명령으로 파일을 쓰다 역슬래시가 사라져 문법 오류가 난 적도 있는데, 테스트를 바로 돌린 덕분에 즉시 발견했습니다 (DEVLOG 문제 11).

| 클라이언트 / 서버 | 브라우저(클라이언트)가 요청하고, 서버가 처리해 답한다 | 브라우저는 화면·저장, 서버 함수는 Gemini 호출 |
| API와 API 키 | 다른 서비스의 기능을 프로그램으로 부르는 창구와 그 비밀번호 | Gemini API, 키는 서버에만 |
| 환경 변수 | 코드 밖에 두는 설정값. 코드를 공개해도 비밀이 안 새게 한다 | `GEMINI_API_KEY`, `ACCESS_CODE` |
| 프롬프트와 구조화 출력 | AI에게 주는 지시문과, 답을 정해진 JSON 형식으로 받는 방법 | 작성 규칙 + 달력표 + 샘플, `responseSchema` |
| AI의 비결정성과 환각 | 같은 입력에도 답이 달라지고, 없는 사실을 만들 수 있다 | 담당자·화자 검사, 사용자 수정 화면 |
| CORS | 브라우저가 다른 사이트에 요청할 때 그 사이트의 허락이 필요하다는 보안 규칙 | 브라우저 → Google 직접 업로드 |
| localStorage | 브라우저 안의 저장 공간. 서버 없이 유지되지만 그 브라우저에만 있다 | 회의 데이터, 양식, 접속 코드 |
| 정적 사이트와 서버 함수 배포 | HTML·CSS·JS는 파일 그대로 제공, `/api/*.js`는 요청 시 실행 | Vercel |
| git과 GitHub | 변경 이력을 기록하는 도구와 그걸 올려 두는 서비스 | 커밋·push → 자동 배포 |
| 단위 테스트 | 함수가 기대한 값을 내는지 자동으로 확인하는 코드 | `tests.mjs` |

## 6. 한계와 개선 방향

- **화자 구분 정확도:** 틀릴 수 있다(테스트에서 6개 중 1개). 실제 여러 사람이 대화한 녹음으로는 추가 검증이 필요하다. 개선: 화자 수를 미리 입력받거나, 전용 화자 분리 모델 사용.
- **AI 결과의 변동:** 같은 녹음을 여러 번 돌리면 결과가 조금씩 다르다. 개선: 핵심 항목(할 일)에 대해 두 번 호출해 교차 확인.
- **양식 모드의 불일치:** 회의록 본문과 할 일 목록을 AI가 따로 쓰므로 가끔 어긋난다. 개선: 본문을 할 일 목록에서 생성하도록 분리.
- **회의 하나만 보관:** 여러 회의를 목록으로 관리하거나 검색하는 기능이 없다. 개선: 회의 목록 + IndexedDB 또는 로그인 기반 DB.
- **캘린더 직접 저장 없음:** 등록 화면을 여는 방식. 개선: 구글 OAuth 연동.
- **데이터 전송:** 무료 등급 Gemini는 입력을 제품 개선에 쓸 수 있다. 기밀 회의에는 유료 등급 또는 다른 처리 방식이 필요하다.
